## 2. 製品仕様(MVP)

### 2.1 製品定義

「委託書店(とらのあな/メロンブックス)とBOOTHの精算書を放り込むと、棚卸まで含めた年間収支が確定し、国税庁作成コーナー/freee/弥生にそのまま持っていける状態になる」確定申告前処理Webアプリ。帳簿アプリでも申告書作成ソフトでもない — **「同人収入の集計と棚卸」だけを完成させる前処理レイヤー**。

### 2.2 コアフロー

```
①精算書アップロード → ②取込確認(振込額突合) → ③(通年)経費・イベント売上入力
 → ④棚卸ウィザード → ⑤年間収支 → ⑥エクスポート/転記ナビ
```

- **UX原則「やることリスト駆動」**: ダッシュボードは常に「申告準備 完成度62%/残り: 12月の精算書が未取込・棚卸が未実施」形式で次の1アクションだけを提示。画面語彙は同人実務語(頒布・委託・精算書・刷り部数)に統一し、税務語には1行注釈
- **①アップロード**: PDF/画像/CSVをドラッグ&ドロップ、発行元はファイル内容から自動判別。とら/メロンはPDF中心【推定】のためLLM-OCRが中核技術、BOOTHはCSV決定的パース
- **②取込確認(信頼の要)**: 原本プレビューと抽出グリッドを左右並置し、「精算書記載の振込額=抽出明細合計」の検算を必ず通す。全件ユーザー承認・自動確定なし。頒布物名は頒布物マスタへ名寄せ提案(棚卸精度の源泉)
- **④棚卸ウィザード**: 「在庫チェック — 12月31日にまだ手元と倉庫に残っている本を数えます」。`刷った部数−(とら販売+メロン販売+BOOTH発送+イベント頒布+見本・破棄)=残部数`を精算書データから自動推計し、ユーザーは確認・修正するだけ。**「書店の倉庫にある在庫もあなたの在庫」**の図解と委託先在庫の照合が実務の最大の落とし穴を塞ぐ。「刷っただけでは経費にならない」を完了画面1枚で説明

### 2.3 無料/有料の機能境界

原則: **「数字は無料で見せる、提出に使う物で課金する」**。無料で通年データを溜めさせ(スイッチングコスト形成)、申告期の「提出物が要る瞬間」がペイウォール。

| 機能 | 無料 | 申告年度パス |
|---|---|---|
| BOOTH CSV取込 | ○ 無制限 | ○ |
| 精算書OCR取込(とら/メロン等) | ○ 年10ファイルまで | ○ 無制限 |
| 取込確認・振込額突合 | ○ | ○ |
| 経費・イベント売上の手入力/頒布物マスタ | ○ | ○ |
| 年間収支ダッシュボード(合計値・所得の目安) | ○ | ○ |
| 棚卸ウィザード | 部数記録まで | ○ 棚卸金額算出 |
| 申告区分別集計表/作成コーナー転記ナビ | ×(マスクプレビュー) | ○ |
| 弥生形式CSV/帳票PDF/明細Excel | × | ○ |
| 過年度データ閲覧 | 直近1年度 | 購入年度は永続 |

BOOTH単体ユーザー(無料代替が豊富)は課金対象にせず口コミ源とする。委託を始めて精算書が複数になった瞬間=無料代替が消える瞬間にペイウォールが一致する。

### 2.5 3申告区分×出力物マッピング

区分はオンボーディングで**ユーザー自身が選択**(アプリは一般基準の提示のみ、判定しない)。データは区分非依存に保持し、出力時に写像する。

## 3. ドメインエンジン(会計ロジックの心臓部)

### 3.1 設計原則(エンジンの憲法)

1. **金額は整数円のみ**(branded type+lintで浮動小数を静的排除)
2. 全チャネルを共通中間表現(`RevenueEvent`/`SettlementStatement`)に正規化。パーサとエクスポータは互いを知らず、エクスポータは`YearCloseResult`のみを読む
3. **検算恒等式が通らないデータは確定させない**(Σ明細=支払額、期首+仕入−期末=売上原価、精算額−振込手数料=入金額)。LLM-OCR由来は特に必須ゲート
4. **エンジンAPIに税務「判定」を返す関数を作らない** — 税理士法52条対策をUI運用でなくドメイン層の設計で構造的に担保
5. 年度依存物(税額表・様式マップ・手数料テーブル)はコードでなく**バージョン付きデータ**(`TaxTable`/`FormSchema`/`FeeSchedule`)。12〜1月の税制改正対応を「新年度データの追加+過去年度テスト凍結」に閉じ込める

### 3.2 チャネル別仕様(Web一次確認済み)

- **とらのあな**: 消化仕入(店頭販売時点で卸成立)。委託手数料は本体価格の30%(買切は40%)、掛率キャンペーンがあるため**掛率は作品×期間単位で保持**。月末締め翌月末払い、毎月25日頃に売上連絡状(2023年10月からインボイス対応の「支払通知書+仕切精算書」構成)。委託分に支払調書・源泉徴収票は発行されない(公式FAQ)。DL販売分は源泉徴収の可能性【推定・実物確認】
- **メロンブックス**: 掛率約70%【推定】。サークルポータルから売上集計と**棚卸データ**をダウンロード可能(会計士事務所解説で確認)— 年末店頭在庫が取れるため差別化機能に直結、実物入手最優先
- **BOOTH**: 売上管理CSV(1日30回・最大31日/回・DL期限3日)。注文×バリエーション単位の複数行で、**注文レベル値は先頭行にのみ記載→注文番号グルーピングで補完**。手数料は2025-10-28改定後「(商品代金+送料)×5.6%+45円/注文」(DL商品は+22円)— 適用開始日付きのFeeScheduleで改定前後両対応。振込は申請ベースのため**年末未振込残高は売掛金として繰越**

### 3.3 会計ロジックの要点

- **発生主義固定**。とら/メロン=精算書の販売月に計上、デフォルトは仕切額の**純額**(精算書と帳簿が1:1突合できる)。BOOTH=注文日ベースで**総額**(手数料は経費)。総額/純額は1,000万円(消費税)・300万円(書類保存義務)の判定に影響する旨を情報提供し、年度内混在はブロック
- **売上原価**: `期首棚卸+当期印刷費(仕入)−期末棚卸`。在庫単価=印刷費÷納品部数(刷=PrintRun単位)。評価方法はデフォルト**最終仕入原価法**(無届出時の法定評価方法)、届出済みユーザー向けに個別法(刷単位)をオプション
- **所在地別在庫**(自宅/とら店頭/メロン店頭/BOOTH倉庫)を追記型ログ(`InventoryMovement`)で管理し、委託先在庫を精算書データと自動照合 — 無料代替のない空白の本丸
- **突合(Reconciliation)**: `精算書の支払額−振込手数料=銀行入金額`のマッチング。全精算書の突合済みフラグが年度締めの完了条件
- **合同誌**: 主催全額負担型/費用分担型(立替精算デフォルト)/売上分配型の3パターンをデータモデルで表現
- **アンソロ原稿料**: 売上と別系統で記録し、源泉徴収税額を申告書の「源泉徴収税額」欄まで一気通貫で伝搬(還付漏れ防止が訴求点)。手取りからの逆算補助(÷0.8979)つき
- **令和8年分の制度前提**: 基礎控除5段階(95/88/68/63/58万円、令和7・8年分限りの上乗せあり→令和9年分は2段階に縮む)を年度別TaxTableで実装。様式は2026年末〜2027年1月公表後2週間でFormSchema差し替え

### 3.4 テスト戦略(申告ミスに直結する品質責任)

1. **会計計算モジュールはカバレッジ100%必須**(端数・掛率・按分・源泉逆算・手数料改定前後)
2. **ゴールデンフィクスチャ**: 実物精算書(需要検証フェーズで収集、匿名化)を`入力→期待正規化JSON`として蓄積。様式変更時は新旧併存
3. **プロパティテスト**: 恒等式(Σ明細=合計/在庫非負/冪等インポート/総額⇄純額切替で最終損益不変)
4. **年度締めE2E**: 「典型サークル1年分」(委託2社+BOOTH+イベント3回+合同誌+原稿料)を**税理士レビュー済み期待値**とスナップショット比較。3区分×2年度=6シナリオ
5. LLM-OCRは別立て評価セット(精算書30枚目標)でフィールド単位F1を計測、モデル更新時に回帰確認。防波堤はあくまで検算ゲート+人間承認

## 4. 技術アーキテクチャ

### 4.1 スタック(単一モノリス・キューレス・ワーカーレス)

| レイヤ | 採用 | 根拠 |
|---|---|---|
| フロント/API | Next.js 15 on Vercel Pro($20/月) | 1リポジトリ1デプロイ。`maxDuration=300s`でLLM-OCRも同一関数内、キュー基盤が初年度不要(5千ユーザー超で滞留したらpgmq後付け) |
| DB/認証/ストレージ | Supabase Pro($25/月) | Postgres+RLS+Auth+Storage一体。RLSで「他人の財務データが見える」事故をDB層で遮断 |
| 決済 | Stripe Checkout(3.6%、Billing/Tax不使用) | 買い切りSKUのため+0.7%のBilling費不要。カード情報は完全委譲(PCI DSS SAQ-A) |
| LLM | Claude API直叩き(Haiku 4.5主力、低信頼時Sonnetエスカレーション、structured output+prompt cache、**同期処理**) | 検算エンジンで品質担保するためBatch不要。モデルIDはconfig化 |
| メール/監視 | Resend / Sentry+UptimeRobot無料枠 | 日次cronで「LLM費/取込失敗率/登録数」をメール1通に集約 |

### 4.2 取込パイプライン

```
アップロード(署名付きURL、SHA-256冪等化) → 形式判定(ヘッダfingerprint/マジックバイト)
 → 決定的CSVパース or LLM-OCR(JSONスキーマ強制) → 検算エンジン(行内/縦計/重複)
 → ユーザー確認UI(全件必須・自動確定なし) → 確定コミット
```

- LLMの自己申告confidenceは使わず、**コード側で決定的に検算**。不一致行はハイライトして手修正

## 7. 法務・コンプライアンス・運用

### 7.1 3つの「やらないこと」で構造的に守る

| やらないこと | 根拠法令 | 担保 |
|---|---|---|
| 個別税務判断(税務相談) | 税理士法2条・52条・54条の2(停止命令制度=刑事罰) | UI文言3問テスト+サポート二値運用+フォーム構造 |
| マイナンバーの取得・保管 | 番号法19・20条(法定事務なき収集は同意があっても違法) | 入力欄なし+アップロード警告+誤受領時は閲覧せず削除 |
| 電帳法の「原本保存先」となること | 電帳法7条 | 免責をアップロード画面直下に常時表示、JIIMA認証は追わない |

- 税理士法の安全地帯は(a)制度の一般的解説(b)操作・計算仕様の説明(c)国税庁一次情報への誘導の3類型**のみ**。全文言に3問テスト: ①特定ユーザーの事実関係への可否判断か ②「あなたの場合は」と読めるか ③選択の代行か — いずれかYESなら書き直し
- **サポート二値運用**: 「操作・仕様」はフル回答/「税務判断」は定型お断り+外部窓口(税務署電話相談・国税庁チャットボット・日税連検索)。問い合わせフォームは「税務のご質問」カテゴリ選択で**送信ボタン自体を無効化**(構造的に受信しない)。全回答ログ保存(調査権限行使時に個別相談していないことを立証可能に)。AI自動回答は導入しない
- 「この経費は落ちますか」への確定版テンプレをFAQ・メール・チャットの3箇所で完全同一文に。OK/NG回答例10組を整備済み(サポートテンプレは公開前に税理士スポットレビュー約5万円)
- 税理士送客は日税連検索サイト・税理士会無料相談への無償リンク+既存紹介サービスのアフィリエイトのみ。**直接提携・紹介料スキームは行わない**(送客時ヒアリングが税務相談に接近するため)
